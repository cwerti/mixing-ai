# План реализации: Архитектура ML (Двухступенчатая каскадная модель)

## 1. Objective (Цель)
Разработать и внедрить архитектуру машинного обучения, способную динамически определять необходимую цепочку плагинов для достижения заданного "референсного" звучания вокала, а также вычислять точные параметры для каждого выбранного плагина.

## 2. Background & Motivation (Контекст)
Мы успешно реализовали программный мост (Bridge) для управления микшером FL Studio, выбора плагинов и установки параметров. Однако жестко закодированные DSP-правила (эвристика) не масштабируются на сотни различных плагинов и сложных эффектов (сатурация, дисторшн, компрессия). Переход к Deep Learning (DL) позволит ИИ "понимать" акустическое влияние каждого плагина. 
Поскольку у нас нет готового датасета, мы используем наш Bridge для автоматической генерации синтетических данных (Self-Play).

## 3. Proposed Solution (Предлагаемое решение)

### Этап 1: Фабрика Данных (Auto-Dataset Generator)
Скрипт, который использует `PluginManager` и `MixerManager` в цикле (offline/batch режиме):
1. Загружает сухой вокальный сэмпл.
2. Выбирает случайную (но валидную) цепочку из фиксированного словаря поддерживаемых плагинов (например: `[EQ -> Compressor]`, `[Saturation -> EQ]`).
3. Генерирует случайные значения параметров (от 0.0 до 1.0).
4. Автоматически рендерит результат через FL Studio.
5. **Сохраняет в датасет:** `Вход: [Спектрограмма Сухого, Спектрограмма Результата]` -> `Выход: [Список плагинов (One-hot encoding), Массив параметров]`.

### Этап 2: Двухступенчатая архитектура моделей (The Cascade Model)
Разделение задачи на две подсети для повышения точности:
*   **Модель A (Архитектор / Классификатор):** 
    *   *Архитектура:* CNN или Audio Transformer (напр., AST).
    *   *Вход:* Спектрограммы Source (исходник) и Target (референс).
    *   *Выход:* Multi-label классификация (вероятности использования каждого плагина из словаря, напр. EQ: 0.9, Delay: 0.1).
*   **Модель B (Инженер / Регрессор):**
    *   *Архитектура:* MLP или RNN.
    *   *Вход:* Спектрограммы Source + Target, плюс вектор выбранных плагинов (от Модели А).
    *   *Выход:* Вектор чисел `[0.0 ... 1.0]`, представляющий положения ручек для выбранных плагинов.

## 4. Implementation Steps (Шаги реализации)
1.  **Определение словаря плагинов:** Составить жесткий список из 5-10 базовых плагинов FL Studio для первой итерации (EQ, Limiter, Compressor, Blood Overdrive, Soundgoodizer).
2.  **Скрипт рендеринга:** Написать утилиту для автоматического рендеринга (bounce) обработанного аудио через командную строку FL Studio или внутренний API.
3.  **Сбор данных:** Прогнать генератор на 50-100 сырых вокальных дорожках, создав 10,000+ вариаций.
4.  **Разработка Модели А:** Обучить классификатор на предсказание архитектуры цепи.
5.  **Разработка Модели Б:** Обучить регрессор параметров с использованием Masked Loss (считать ошибку только для тех параметров плагинов, которые были реально использованы).
6.  **Интеграция:** Подключить модели к `app/core/full_pipeline.py`.

## 5. Pitfalls & Risks (Подводные камни и риски)

*   **Проблема автоматического рендеринга:** Наш Bridge отлично "крутит" ручки в реальном времени, но для датасета нужно *экспортировать* звук. Автоматизация рендера в FL Studio (через меню File -> Export) нестабильна при эмуляции клавиш. *Решение:* Использовать параметры командной строки FL Studio (`fl.exe /R /E...`) для batch-экспорта, если это возможно, или использовать сторонний VST (например, Melda) для записи выхлопа в файл прямо в микшере.
*   **Комбинаторный взрыв параметров:** Если мы поддерживаем 20 плагинов по 10 параметров, выходной вектор регрессии равен 200. Обучить сеть на 200 параметров одновременно крайне сложно (проклятие размерности). *Решение:* Строго ограничить словарь плагинов на старте. Использовать Masked Loss.
*   **Акустическая неоднозначность (Ill-posed problem):** Разные комбинации плагинов могут давать идентичный звук (например, поднять громкость на EQ или на Компрессоре). Модель может "запутаться", получая противоречивые градиенты. *Решение:* Ввести штрафы (regularization) за использование лишних плагинов. Учить сеть выбирать простейшую цепь.
*   **Смещение датасета (Dataset Bias):** Если для генерации использовать только 10 сухих дорожек, модель переобучится на их тембры и не будет работать с новыми голосами. *Решение:* Собрать максимально разнообразный корпус сухого вокала (мужской, женский, разный темп, разное качество микрофона) перед запуском генератора.
*   **Порядок плагинов:** Влияние плагинов некоммутативно (EQ -> Comp звучит иначе, чем Comp -> EQ). *Решение:* На первом этапе зафиксировать порядок слотов (Слот 1: всегда Сатурация, Слот 2: всегда EQ и т.д.). Позже перевести Модель А на предсказание последовательности (Seq2Seq / RNN).

## 6. Verification (Проверка)
1. Написание юнит-тестов для скрипта генерации (проверка валидности маппинга параметров 0-1 в MIDI).
2. Оценка Модели А по метрике F1-score (насколько точно угадывает нужные плагины).
3. Оценка Модели Б по метрике Mean Squared Error (MSE) на параметрах.
4. Слуховое (A/B) тестирование синтезированного пресета против оригинального (тест Тьюринга для миксинга).
