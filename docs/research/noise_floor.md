# Шум оценки на 8 реальных парах: сколько считать улучшением

Дата: 2026-10-31. Ветка `feat/chain-benchmark`. Модель v6 (`data/models/v6/best_model.pth`), целевая функция
`embedding`, `patience 60`. Метрика — ошибка log-mel результата против истинного wet того же фрагмента
(`logmel_db`, дБ, среднее по 8 парам). Сырые данные: `data/runs/benchmark/noise/*.jsonl`.

Код: все прогоны стартовали до 16:02 и шли на коде `8a23bef` плюс `max_renders`. Коммит `e6ba386` (дилей:
сетка по времени, проверка вместе с ревером) их не затронул. Абсолютные значения для HEAD надо перемерить
тем же протоколом. Пороги шума, скорее всего, переносятся, но дилей добавляет еще одну многоэкстремальную
ось.

## Коротко

1. **Режим model детерминирован.** Повтор совпал с v9 бит в бит на всех 16 случаях.
2. **Бюджет 60 с невоспроизводим.** При том же seed 2 случая из 32 дали другую цепочку. Худший пример:
   oxeye_backing1 cross, optimizer — 0.99 против 3.19 дБ. Из-за этого среднее по cross сдвигается на 0.28 дБ.
   **Бюджет в рендерах (`--max-renders 200`) воспроизводим бит в бит**: 32 из 32 цепочек совпали. По времени
   он не дороже: около 16 мин на seed для обоих режимов против примерно 19 мин у 60 с.
3. **Разброс между seed на cross большой: σ среднего по 8 парам 0.13–0.20 дБ.** Он почти весь сидит в 4 парах:
   ronnie (до 1.1 дБ), oxeye_backing2 (0.6), whiptails (0.4–0.6) и oxeye_leadvox (0.1–0.25). На same шум
   слабый (σ 0.05). Его дает только whiptails: на остальных 7 парах same CMA-ES не запускается вообще
   (1 рендер).
4. **Вывод v9 «model+optimizer на cross лучше optimizer: 2.18 против 2.58» — шум одного seed.** Повторный
   прогон того же seed дал optimizer 2.29. На 5 seed разница в пользу optimizer: +0.06 дБ при 60 с и
   +0.25 дБ при 200 рендерах. Обе незначимы: sign-flip по парам p = 0.88 и 0.63.
5. **Правило.** Изменение считается улучшением, если на протоколе ниже выполнены оба условия:
   - (а) среднее cross log-mel по 5 seed падает минимум на **0.35 дБ**; на same — минимум на 0.10 дБ;
   - (б) выигрыш остается > 0, если выкинуть пару с самым большим выигрышем.

   Одиночный seed ничего не доказывает, пока разница меньше 0.8 дБ.

## Протокол

```
python scripts/real_pairs.py --model-path data/models/v6/best_model.pth --metric embedding \
    --modes model+optimizer optimizer --max-renders 200 --seed 0 1 2 3 4 --listen-dir= \
    --out data/runs/benchmark/noise/renders200_s1-4.jsonl --audio-tmp data/runs/benchmark/noise/audio_renders200_s1-4
```

Что добавлено для протокола (обратно совместимо):
- `ChainOptimizer.optimize(max_renders=...)` и `ChainBenchmark.run_case(max_renders=...)`. Предел проверяется
  после каждого поколения CMA-ES, поэтому перелет — не больше одного поколения (до 210 рендеров при пределе 200);
- в `scripts/real_pairs.py`:
  - `--seed` (несколько seed подряд; source и wet_true пишутся один раз);
  - `--max-renders` (без явного `--budget` время не ограничено);
  - `--listen-dir=` (пустое значение — папку прослушивания не писать);
  - в jsonl добавлены поля `budget_s`, `patience`, `max_renders`.
  Раньше seed был зашит в 0;
- тест `test_max_renders_caps_search_and_is_reproducible`.

## Воспроизводимость

| Сравнение | Совпало цепочек | Средний / максимальный \|Δ log-mel\| |
|---|---|---|
| model: этот прогон против v9 | 16/16 | 0 / 0 |
| 200 рендеров: seed 0 против повтора | 32/32 | 0 / 0 |
| 60 с: seed 0 против повтора | 30/32 | 0.069 / **2.20** (oxeye_backing1 cross, optimizer) |
| 60 с: seed 0 против v9 (та же модель, прогон накануне) | 29/32 | 0.017 / 0.43 (oxeye_leadvox cross, model+optimizer) |

Откуда шум времени: часть cross-случаев упирается в 60 с, не дойдя до `patience` (до 298 рендеров). Число
поколений CMA-ES тогда зависит от загрузки машины, а на многомодальной целевой функции одно лишнее поколение
меняет итоговую цепочку. Сам seed передается в CMA-ES (`seed + 1`). В остальном рендер и `embedding` на CUDA
дали бит-в-бит одинаковый результат.

Доля времени в общем шуме небольшая: σ между seed при 60 с и при 200 рендерах почти одинаковая (таблица ниже).
Время добавляет невоспроизводимость, а не дополнительный разброс. Но из-за нее нельзя повторить прогон и
посмотреть именно ту цепочку, что дала цифру.

## Минимальная различимая разница

Две системы, у каждой S seed. Стандартная ошибка разности средних: SE = σ·√(2/S), где σ — разброс среднего
по 8 парам между seed. Seed разных систем не связаны: у model+optimizer и optimizer разные стартовые точки, и
спаривание по seed не уменьшает шум. Порог значимости — 1.96·SE. Порог, который настоящий эффект такой
величины проходит с вероятностью 80 %, — 2.8·SE.

| Вариант | σ (худший режим) | S = 1 | S = 3 | S = 5 |
|---|---|---|---|---|
| cross | 0.20 | 0.57 / 0.81 | 0.33 / 0.47 | **0.25 / 0.36** |
| same | 0.05 | 0.14 / 0.20 | 0.08 / 0.11 | **0.06 / 0.09** |

В ячейках: порог 95 % / порог 80 % мощности (дБ). Проверка без модели: разница между непересекающимися группами
seed одной и той же системы доходила до 0.50 дБ при 1 seed против 1 и до 0.32 дБ при 2 против 2 (cross).

Этот порог учитывает только шум seed. Пар всего 8, и выигрыш часто дает одна пара. Пример: model+optimizer
против optimizer на cross при 200 рендерах.
- разница +0.25 дБ (optimizer лучше), по парам: 0, 0, 0, 0, +0.28, 0, **+2.03**, −0.35;
- sign-flip по парам: p = 0.63;
- бутстрап по парам и seed: 95 % ДИ [−0.17; +0.87].

Поэтому к порогу добавлено условие (б) — устойчивость к выбросу одной пары.

## Правило

Сравнение двух вариантов (модель, метрика, оптимизатор):
1. Протокол: `--max-renders 200 --patience 60`, seed 0–4, оба варианта на одной машине. Бюджет в секундах для
   сравнений не использовать.
2. Улучшение засчитывается, если:
   - среднее cross log-mel по 8 парам × 5 seed ниже минимум на **0.35 дБ**;
   - на same оно не хуже больше чем на 0.10 дБ;
   - после удаления пары с наибольшим выигрышем разница остается > 0.
3. Разница 0.25–0.35 дБ — «вероятно»: нужно еще 5 seed (5–9) или больше пар.
   Разница < 0.25 дБ — неотличимо от шума.
4. По одному seed выводы делать только при разнице ≥ 0.8 дБ. Иначе — «нужен прогон на 5 seed».
5. В отчете приводить таблицу по парам (среднее и диапазон). Цифры ronnie, oxeye_backing2 и whiptails
   с разницей меньше 1 дБ — шум.

## Что это меняет в прошлых выводах

- `domain_randomization.md`, п. 2: «model+optimizer на cross лучше optimizer (2.18 против 2.58)» не
  подтверждается. На 5 seed разница ничейная или в пользу optimizer: 2.47 против 2.41 при 60 с, 2.59 против 2.34
  при 200 рендерах. Значение 3.19 у optimizer на oxeye_backing1 — вариант времени, а не seed: повтор того же
  seed дал 0.99. Выигрыш model+optimizer на whiptails (−0.35) и oxeye_backing1 держится. Проигрыш на ronnie
  (+2.0 дБ в среднем, разброс 4.3–7.3) — реальный и самый большой источник шума.
- Строка v6 «model: 1.77 / 2.19» детерминирована и верна.
